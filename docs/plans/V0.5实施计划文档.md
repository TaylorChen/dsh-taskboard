# dsh-taskboard V0.5 实施计划

> 状态：待实施 · 基线 `v0.4.0` (`67a8303`) · 目标 `0.5.0` · ROADMAP **L2 规格层**
> 本文是实施依据。沿用既有流程：为什么 / 改哪里 / 怎么算完成 / 风险。

---

## 一、背景（第一性原理）

L1 执行层（v0.1–v0.4）跑通后暴露的瓶颈是：**agent 领了任务不知道怎么做**。
"修复登录 bug" 对人足够，对 agent 不够——它不知道代码在哪、成功长什么样。
ROADMAP 的 L2 结论：**任务的本质从「描述」变成「可执行规格」**，任务板的第一
职责从「追踪进度」变成「把意图翻译成自包含规格」。

v0.5 把 `draft` 状态从「空的占位列」升级为「规格不完整的任务」——`draft` 的
语义成为真实约束：**只有规格完整的任务才能进入 `open`（可被认领）**。

## 二、范围

### 做

| 编号 | 工作项 | 破坏性 | 依赖 |
|---|---|---|---|
| **W1** | 任务规格字段：`spec { acceptanceCriteria, contextRefs, definitionOfDone }` | 否（加法） | — |
| **W2** | `draft` 语义化：规格完整性作为进入 `open` 的前置条件 | 否（行为） | W1 |
| **W3** | 工具与面板：模型可见规格、创建缺规格自动落 draft、draft 列完整性提示 | 否 | W1/W2 |

### 不做（附理由）

| 不做 | 理由 |
|---|---|
| 规格的 schema 校验（zod 只做形状，不做语义） | 启发式足够：验收标准是硬门槛，上下文引用是软提示，避免误伤无文件引用的任务 |
| 打回（awaiting_human → draft） | v0.6 验证闭环一起做，打回需要「证据 + 原因」语义 |
| 规格模板 / 自动生成规格 | 需要模型参与，属于「创建时注入」的 v0.8 范畴 |

## 三、工作项详述

### W1 · 规格字段

**改动点。**

- `src/domain.ts` — 新增：
  ```ts
  export const taskSpecSchema = z.object({
    acceptanceCriteria: z.array(z.string().min(1)).max(32).default([]),
    contextRefs: z.array(z.string().min(1)).max(32).default([]),
    definitionOfDone: z.string().max(2000).default(''),
  })
  ```
  `taskSchema` 增加 `spec: taskSpecSchema.nullable().default(null)`——`null` =
  未规格化；老记录无此字段解析为 `null`（与 `origin`/`blockedReason` 同模式，
  不 bump `DOMAIN_VERSION`）。
- 导出/导入：spec 随 taskSchema 走，加法兼容；导入的旧文档 spec 为 null。

**验收**

- [ ] 老记录（无 spec）读出来 `spec === null`
- [ ] 新任务可带完整 spec 落盘

### W2 · draft 语义化 + 规格检查

**核心不变量：`open` = 可执行 = 规格完整。** 认领/派发不再检查规格（open 天然
保证），`autoClaim` 不变。

**改动点（`src/service.ts`）。**

- 纯函数 `isSpecComplete(spec): boolean` —— `spec !== null && acceptanceCriteria.length > 0`。
  contextRefs 是软提示：缺失只影响面板提示，不阻止进入 open（理由：验证类任务
  可以没有文件引用）。
- `create`：显式 `status: 'open'` 但规格不完整 → **自动落 `draft`**（不报错；
  模型建任务常缺规格，报错会打断流程）。显式 `status: 'draft'` 或未给规格时
  默认仍走 draft（当规格缺时）。
- `update`：**迁入 `open` 必须规格完整**，否则 `invalid-input`（提示缺什么）。
  覆盖 `draft → open`、`awaiting_human → open`、任何状态 → open。
- `CreateTaskInput` / `UpdateTaskInput` 增加：
  - `acceptanceCriteria?: readonly string[]`、`contextRefs?: readonly string[]`、
    `definitionOfDone?: string`
  - update 的 spec 是**部分更新**：patch 提供任一 spec 子字段时，在现有 spec
    基础上合并（当前 spec 为 null 时创建新 spec 块，其余子字段用默认）。

**验收**

- [ ] 创建时给 `status: 'open'` 但无验收标准 → 任务落 `draft`
- [ ] 创建时给完整规格 + `status: 'open'` → 任务落 `open`
- [ ] `update` 迁入 open 但规格不完整 → `invalid-input`
- [ ] 补全规格后 `draft → open` 成功
- [ ] 规格部分更新：只改 contextRefs 不丢 acceptanceCriteria
- [ ] `isSpecComplete` 纯函数单测

### W3 · 工具与面板

**改动点。**

- `src/tool.ts`：
  - `task_create` 参数加 `acceptance_criteria: string[]`、`context_refs: string[]`、
    `definition_of_done?: string`
  - `task_update` 同上（补规格用）
  - `taskValueSchema` 投影加 `acceptance_criteria: string[]`；render 里状态行后加
    `criteria: a; b; c`（有则显示）——模型能看到任务是否可执行
  - `renderDispatchPrompt`（autoclaim）把规格写进子代理 prompt：逐条验收标准 +
    contextRefs + definitionOfDone
- `src/client/TaskboardView.tsx`：
  - draft 列卡片：规格不完整时显示提示（「缺验收标准」硬提示 / 「缺上下文引用」
    软提示），不完整时给警示色
  - `BoardTask` 接口加 `spec`
- `src/routes.ts`：`PATCH` 透传 spec 子字段；`POST` 透传

**验收**

- [ ] 模型 `task_create` 不给验收标准 → 返回的任务是 `draft`
- [ ] 模型 `task_update` 补 `acceptance_criteria` 后可迁移 open
- [ ] `task_list` 的 render 含 `criteria:`
- [ ] 派发 prompt 含验收标准逐条
- [ ] 面板 draft 卡片显示完整性提示

## 四、实施顺序

W1（字段）→ W2（约束）→ W3（工具/面板）——W2 依赖 W1，W3 依赖前两者。

## 五、破坏性变更与回滚

| 变更 | 破坏性 | 处理 |
|---|---|---|
| `spec` 字段 | 否 | 加法，`.default(null)`，老记录解析为 null |
| 「open 需规格完整」约束 | 行为变更 | 旧 open 任务可能缺规格——**迁移**：老 open 任务若无 spec，读侧不强制（约束只在新写入时生效），面板提示补规格；自动认领对无 spec 的 open 任务照常（不阻断存量） |
| 创建缺规格自动落 draft | 行为变更 | 新行为，旧数据不受影响 |

**回滚**：`git reset --hard v0.4.0`。无迁移负担。

## 七、风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 「open 需规格」误伤存量 open 任务 | 中 | 约束只在新写入时生效；存量任务面板提示补规格，不阻断 |
| 模型不会填规格字段 | 中 | prompt/工具描述写明；缺规格自动 draft 是兜底而非失败 |
| 规格字段沦为摆设 | 低 | 派发 prompt 强制消费规格（子代理按验收标准执行），让字段有用 |
