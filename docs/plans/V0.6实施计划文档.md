# dsh-taskboard V0.6 实施计划

> 状态：待实施 · 基线 `v0.5.0` (`682e337`) · 目标 `0.6.0` · ROADMAP **L3 验证闭环**
> 本文是实施依据。沿用既有流程：为什么 / 改哪里 / 怎么算完成 / 风险。

---

## 一、背景（第一性原理）

v0.5 让任务带着可执行规格进入 `open`，派发时子代理按验收标准执行。但完成回写
仍然是 `completed → awaiting_human`——**人需要重查子代理做了什么**。L3 的结论：
信任问题——**agent 说完成了不等于完成了**；人的时间应该花在确认结论，不是重跑
执行。v0.6 把「完成」变成「**有证据的完成**」：证据自动收集、验收标准逐条自评、
失败自动带诊断，人只需确认或打回。

## 二、范围

### 做

| 编号 | 工作项 | 破坏性 | 依赖 |
|---|---|---|---|
| **W1** | 结构化证据：派发用 `outputSchema` 约束子代理报告，`settleDispatch` 存 `evidence` | 否（加法） | v0.5 规格 |
| **W2** | 失败诊断：`error` 结算自动 attach 失败摘要 | 否 | W1 |
| **W3** | 面板：`awaiting_human` 显示证据 + 确认/打回按钮 | 否 | W1 |

### 不做（附理由）

| 不做 | 理由 |
|---|---|
| 自动跑测试作为证据 | 子代理执行本身会跑；板子只负责收集其报告，不自己起测试（那是执行器的职责） |
| 证据的 schema 强校验语义 | `outputSchema` 只保证形状；met/met 的判定交给子代理自评，人是最终裁判 |
| 经验卡 / 结论归档 | v0.8 知识层一起做（依赖证据结构） |

## 三、工作项详述

### W1 · 结构化证据

**为什么。** 目前 `settleDispatch('completed')` 只迁移状态，子代理「做了什么」的
证据丢在子会话日志里，人看不到。

**设计。** `ctx.subagents.start` 支持 `request.outputSchema`（Spike S4 已验证的
公开能力）：派发时给子代理一个结构化报告 schema，子代理完成时按它输出，
`run.result.structured` 就是证据。parent 校验后存进任务。

**改动点。**

- `src/domain.ts` — 新增：
  ```ts
  export const evidenceSchema = z.object({
    criteria: z.array(z.object({
      criterion: z.string().min(1),
      met: z.boolean(),
      note: z.string().max(2000).default(''),
    })).default([]),
    artifacts: z.array(z.string().min(1)).max(32).default([]),
    summary: z.string().max(4000).default(''),
  })
  ```
  `taskSchema` 增加 `evidence: evidenceSchema.nullable().default(null)`（加法）。
- `src/autoclaim.ts`：
  - 派发 prompt 末尾要求子代理按输出 schema 报告（自评每一条验收标准 + 产物 +
    摘要）
  - `subagents.start(..., { ..., outputSchema })`（outputSchema 用
    `assertObjectJsonSchema` 允许的子集：object/array/string/boolean）
- `src/service.ts`：
  - `settleDispatch` 的 `completed` 分支接受 `evidence`，写入任务
  - 新增只读 `evidenceOf(ref)` 返回证据（面板用）

**验收**

- [ ] 子代理完成 → 任务带 `evidence.criteria`（逐条 met/note）、`artifacts`、`summary`
- [ ] 子代理输出不符合 schema → 视为 `error` 结算（不存半截证据）
- [ ] 老记录 `evidence === null` 兼容

### W2 · 失败诊断

**为什么。** `error` 结算目前只有 `blockedReason: "subagent X ended with error"`，
人看不到失败在哪。

**改动点（`src/autoclaim.ts` + `service.ts`）。**

- `error` 分支：从 `run.result.output`（子代理部分输出）截取最后一段 + stop reason，
  组装诊断文本
- `settleDispatch` 的 `error` 分支把诊断放进 `evidence.summary`（并保持
  `blockedReason` 为人类可读原因）

**验收**

- [ ] error 结算 → 任务 `blocked` 且 `evidence.summary` 含诊断、`blockedReason` 可读
- [ ] 诊断文本有长度上限

### W3 · 面板确认/打回

**为什么。** 「有证据的完成」闭环的最后一步是人的动作：确认（→ done）或打回
（→ draft，规格不完整 / → open，可重新执行）。

**改动点（`TaskboardView.tsx` + `locales.ts`）。**

- `awaiting_human` 卡片：显示 `evidence.criteria` 自评（✓/✗ + note）、
  `artifacts`、`summary`
- 卡片上「确认完成」（PATCH status → done）与「打回」（PATCH status → draft）
  按钮（human 写，无审批）
- 打回到 open 需要规格完整——由服务层 v0.5 门保证，面板打回按钮直接走 draft

**验收**

- [ ] awaiting_human 卡片显示证据清单
- [ ] 确认 → done；打回 → draft，活动流记录迁移

## 四、实施顺序

W1（证据收集）→ W2（失败诊断）→ W3（面板）。

## 七、风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 子代理不按 outputSchema 输出 | 中 | 按 error 结算（不存半截证据）；prompt 明确要求 |
| outputSchema 形状超出 `assertObjectJsonSchema` 子集 | 中 | 只用 object/array/string/boolean，不用 pattern/format |
| 自评不诚实（met 乱标） | 低 | 自评是给人的加速器，人是最终裁判；note 要求引用证据 |
