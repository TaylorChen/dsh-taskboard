# dsh-taskboard V1.1 实施计划

> 状态：待实施 · 基线 `v1.0.0` (`d92f151`) · 目标 `1.1.0`
> 本文是实施依据。v1.1 = 止损 + 闭环：执行失控能打断、执行过程可见、打回带着原因。

---

## 一、背景（第一性原理）

v1.0 已闭环「定义 → 规格 → 执行 → 证据 → 确认」。但信任闭环有三处硬缺口：

1. **执行失控无法止损**。任务派发后，子代理在独立会话里跑——人工接管、部署停止、
   任务作废时，**没有任何机制取消它**（继续烧 token、可能改错东西）。`run.dispose`
   能力存在但未接线。
2. **执行过程不可见**。`in_progress` 的任务，人不知道它「活着还是卡死」——
   看不到子会话、跑了多久。信任的前提是可见。
3. **打回不带原因**。面板「打回待立项」只是状态迁移，下个执行者不知道改什么。
   闭环语义断裂。

## 二、范围

### 做

| 编号 | 工作项 | 破坏性 | 依赖 |
|---|---|---|---|
| **A1** | 派发取消与超时：任务离开 `in_progress` 时取消子代理；超时自动受阻 | 否 | — |
| **A2** | 执行可见性：面板显示执行中的子代理 id + 时长 | 否 | — |
| **B1** | 打回原因：面板打回必填原因（写入 note） | 否 | — |

### 不做（附理由）

| 不做 | 理由 |
|---|---|
| 执行中进度（token 用量实时上报） | 需要子代理内埋点，超出插件边界；「活着 + 时长」已够止损 |
| 取消的审批确认 | 取消是止损动作，及时性优先于确认（任务状态迁移本身已过审批/人工） |
| 队列/重试策略 | v1.2 治理一起评估；v1.1 只做「能停」 |

## 三、工作项详述

### A1 · 派发取消与超时

**为什么。** 执行失控的代价是 token 与副作用；止损必须可触发且自动。

**设计。** autoclaim 驱动维护进程内 `executions: Map<taskId, { run, runId, startedAt }>`：

- **取消接线**：监听 storage-domain 的 `domain/changed`（该域的表/键变更事件），当某
  `in_progress` 且派发中的任务被改成其它状态（人工接管/作废）→ `run.dispose()` 并
  从映射移除。dispose 后子代理若已 settle，settle 回调照常（先查映射确认仍归本
  驱动管）。
- **超时**：`Config.dispatchTimeoutMs`（默认 30 分钟）。派发时登记 `startedAt`；
  定时扫描（复用驱动的 idle 循环或 `setTimeout` 链）发现超时 → `dispose()` +
  `settleDispatch({ kind: 'error', reason: '执行超时', diagnosis })`。
- 服务层不需要新字段；取消/超时的语义通过已有的 `settleDispatch`（error）表达。

**验收**

- [ ] 派发中的任务被人工移到 done/blocked → 子代理被 dispose（单测：fake run 有
      dispose spy；驱动集成测试：emit domain/changed 后断言 dispose 被调）
- [ ] 超时未 settle → 自动 dispose + 任务 blocked「执行超时」
- [ ] dispose 后迟到的 run.result settle 不会重复结算（映射已移除 → 跳过）
- [ ] 未派发任务不受影响

### A2 · 执行可见性

**为什么。** 人需要知道「球在 agent 手上时，agent 活着且在做」。

**设计。** A1 的 `executions` 映射同时是可见性数据源：

- service 新增只读 `executionOf(ref): { subagentId, startedAt } | undefined`，
  通过 `setExecutionTracker(tracker)` 注入（autoclaim 提供；无注入返回 undefined）
- routes `/board` 响应带 `executions: Record<taskId, { subagentId, startedAt }>`
- 面板：`in_progress` 卡片显示「执行中 · `subagentId` 前 N 分钟」

**验收**

- [ ] `executionOf` 返回派发中的执行信息；未派发/未注入返回 undefined
- [ ] `/board` 带 executions
- [ ] 面板显示执行徽标（渲染逻辑；上屏留给真实环境）

### B1 · 打回原因

**为什么。** 打回是闭环语义的一部分：下个执行者必须知道改什么。

**设计（纯面板 UX，服务层已有能力）。**

- 面板「打回待立项」点击 → 弹原因输入（必填）→ `PATCH { status: 'draft', note: 原因 }`
- 原因通过 `note` 追加落盘（活动流记 `noted` + `status` 两条，可完整还原打回）

**验收**

- [ ] 打回必填原因，空原因不发起
- [ ] 打回后任务 notes 含原因、活动流有 noted + status（服务层已有测试覆盖，面板
      逻辑走 API 路径验证）

## 四、实施顺序

A1（驱动侧：映射+取消+超时）→ A2（暴露）→ B1（面板）。

## 五、破坏性变更与回滚

无 schema 变更；`git reset --hard v1.0.0` 可回滚。

## 六、验证清单

**代码层**：check/build 全绿；单测 + 驱动集成测试（dispose spy、超时假时钟、
重复 settle 防重、executionOf）。

## 七、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| domain/changed 事件语义与预期不符 | 中 | 先做 30 分钟 Spike 确认事件载荷，结论入 ARCHITECTURE |
| dispose 后 run.result 竞态 | 低 | 映射移除后跳过 settle（幂等） |
| 超时扫描开销 | 低 | 每任务一个 setTimeout 链，不做全局轮询 |
