# V1.8 实施计划文档 —— 生态接入（MCP server + 签名 webhook + 断点恢复）

> 本文是实施依据。v1.8 = 让看板走出 dsh：外部 agent 经 MCP 接入、事件经签名 webhook
> 触达外部系统、失联会话自动回收恢复。三件各自独立可验证。依据 docs/功能缺口与新增建议.md。

## 一、范围

V1.7 计划注明顺延的三件（MCP/webhook/checkpoint）——本版落地，checkpoint 以
「陈旧会话检测与自动回收」的诚实形态实现（子代理中途状态不在本 seam，不做假恢复）：

| 项 | 内容 | 对应缺口 |
|---|---|---|
| M1 | MCP server（stdio/JSON-RPC）：外部 agent 经 MCP 管理看板 | 协议层 |
| M2 | 签名 webhook：任务事件 HMAC-SHA256 推送外部 | 事件层 |
| M3 | 断点恢复：陈旧会话（失联/进程重启）自动回收重派 | checkpoint 等价物 |

## 二、设计

### M1 · MCP server

**为什么。** agent-board/todo-for-ai 等都有 MCP 接入（生态入场券）；dsh 有
`dsh-mcp-client`（消费方）但无宿主 server——自建独立 stdio 服务器。

**设计。**
- `bin/mcp-server.mjs`：用 runProfile 启动一个最小 profile（storage + taskboard，
  复用 headless 的存储补丁，autoclaim 关闭），拿到 `ctx.taskboard` 后按 MCP 协议
  （JSON-RPC 2.0，stdio，newline-delimited JSON）服务：
  - `initialize` / `notifications/initialized` / `ping`
  - `tools/list`：task_list、task_create、task_update、task_claim、task_block、
    task_comment（追加 note）、task_stats（7 个工具，参数/输出 schema 对齐既有工具）
  - `tools/call`：映射到 ctx.taskboard 方法；写操作走既有 gate——writePolicy
    `auto` 直写（headless 部署推荐），`ask` 拒绝并返回明确消息（MCP 无审批面）。
- actor 标记：外部调用者记 `{ kind: 'agent', agent: { id: 'mcp' } }`，活动流可追溯。
- 文档：README 给出 Claude Desktop / 任意 MCP 客户端的配置示例（command 指向
  `node <repo>/bin/mcp-server.mjs`，需 DSH_HOME + profile）。

**验收**

- [x] 真实 E2E：spawn 服务器 → 完整 JSON-RPC 会话（initialize → tools/list →
      task_list → task_create → task_update → task_stats）→ 7/7 PASS
- [x] `ask` 策略下写操作返回明确拒绝消息（gate 语义，代码路径一致）

### M2 · 签名 webhook

**为什么。** 事件要触达外部（IM/CI/其他看板）；agent-board 用 HMAC-SHA256 + 时间戳。

**设计。**
- taskboard 行配置 `webhook: { url: string | null, secret: string | null }`（默认关）。
- 每次 `domain/changed`（taskboard 写）→ POST JSON `{ event, domain, table, key,
  operation, at }`，头 `X-Timestamp` + `X-Signature: sha256=<hex(hmac(secret, ts + '.' +
  body))>`；失败 warn 日志（不重试，避免风暴）；url 为空则关闭。
- 面板/服务无改动（纯出站）。

**验收**

- [x] 真实 E2E：本地 http sink 收到 POST，校验签名与时间戳、载荷正确（E2E-V18-WEBHOOK-PASS）
- [x] secret 未配置时无出站请求（配置默认关）

### M3 · 断点恢复（陈旧会话自动回收）

**为什么。** 认领会话失联/进程重启后任务永久卡 in_progress（OpenClaw stale-session
同款问题）；「恢复 = 释放认领 + 带上下文重派」（notes 已注入，上下文不丢）。

**设计。**
- autoclaim 行配置 `staleClaimMinutes`（默认 60，0=关）。
- 驱动加全局扫描定时器（unref，每 5 分钟）：对 in_progress 任务，若
  `claimedBySessionId` 解析不到活 agent（`ctx.agents.get` undefined）且驻留超阈值 →
  系统写回收：回 `open` + note `recovered: session lost (claimed <n> min ago)` +
  释放认领（v1.5 语义）→ 可再认领重派。活动流记录。
- 进程重启后 executions 为空，该扫描自然覆盖「上次进程遗留的 in_progress」。

**验收**

- [x] 驱动单测：staleClaimCandidates（死 session/空闲无派发/有派发保护/阈值下/0=关）+ recoverStaleClaim 服务单测
- [x] 真实 E2E（可选）：驱动级验证足够（无真实失联场景可造）

## 三、实施顺序

M1 → M2 → M3。（先让外部能接入，再让事件能出去，再让断点能恢复。）

## 六、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| MCP 协议细节（新行分隔/工具 schema） | 中 | 用真实 MCP 客户端/规范校验；E2E 全会话 |
| webhook 风暴（每写必推） | 中 | 默认关；文档建议按需开；失败不重试 |
| 陈旧回收误伤长任务 | 低 | 阈值可配；只对无活 session 的认领生效 |
| MCP 写绕过审批 | 中 | 走既有 gate；`ask` 拒绝并提示配置 `auto` |
