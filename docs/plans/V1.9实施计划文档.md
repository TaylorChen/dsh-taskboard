# V1.9 实施计划文档 —— 度量治理闭环（失败模式 + agent 对比 + CFD + 主动告警）

> 本文是实施依据。v1.9 = 把统计报表升级为治理工具：失败可分类、agent 可对比、
> 流程可外推、异常能主动触达。依据 docs/功能缺口与新增建议.md 二·五节。

## 一、范围

调研定稿的 P0 五项中，成本归因的「$ 换算」依赖模型单价（超出本 seam），以
「per-agent 成本分解 + 超支告警」落地；五项合并为四项：

| 项 | 内容 | 调研对应 |
|---|---|---|
| G1 | 失败模式分布：stats 按 settle 失败原因分类 | P0-失败模式 |
| G2 | agent 维度对比 + 成本分解：按认领会话切片 | P0-agent 对比 / 成本归因 |
| G3 | CFD 累积流图：近 14 天逐状态日末计数 | P0-CFD |
| G4 | 主动告警：超时/超支/受阻结算/陈旧回收 → webhook alert 事件 | P0-告警 |

## 二、设计

### G1 · 失败模式分布

**为什么。** 重做率只是总数；loop/stuck/thrash/timeout/成本失控要分类才能诊断。

**设计。** `stats()` 增加 `failureModes: Record<mode, number>`——遍历 blocked 任务，
按 `blockedReason` 模式分类（不加 schema）：
- `timeout`（含「execution timed out」）、`budget`（含「token budget」/「over
  budget」）、`no-report`（含「without a structured report」）、`infra`（含
  「failed to run」）、`other`（兜底）。
面板统计区加一行「失败分布」。

**验收**

- [x] 单测：构造各原因 blocked 任务 → failureModes 分类正确（5 类各 1）
- [x] `/stats` 返回字段（HTTP E2E 顺带断言）

### G2 · agent 维度对比 + 成本分解

**为什么。** 同一任务集下哪个 agent 一次做对率高、成本低——路由决策前提（难度归一化
需文档注明）。

**设计。** `stats()` 增加 `byAgent: Array<{ agent, settled, success, rework, avgCycleMin, tokens }>`：
按认领会话（claimed 活动条目 actorLabel）聚合——settle 成败、打回数、cycle 平均、
tokensUsed 合计。认领会话即执行 agent（子代理由其派生，如实标注「以认领会话计」）。

**验收**

- [x] 单测：两个 session 各异的历史 → byAgent 各字段正确（success/rework/tokens）
- [x] 无认领历史时为空数组

### G3 · CFD 累积流图

**为什么。** 卡点检测是静态快照；CFD 看队列堆积趋势、可外推交付。

**设计。** `stats()` 增加 `cfd: Array<{ day, counts: Record<status, number> }>`——近
14 天每日末各状态任务数，由活动流时间线重建（同 v1.5 dwell 的 walk；活动流保留上限
导致老任务早期段缺失，文档注明）。面板统计区加 14 天迷你堆叠条（纯 CSS）。

**验收**

- [x] 单测：已知时间线 → 今日日末 done/blocked 计数正确
- [x] 面板渲染（bundle 含按 agent/近 14 天流动文案）

### G4 · 主动告警（webhook alert 事件）

**为什么。** 卡点/超时/超支不能等人来查；M2 webhook 已有，缺的是失败事件源。

**设计。** autoclaim 在四类事件触发 `webhook` alert 推送（复用 M2 的签名通道，新增
`event: taskboard.alert` 载荷字段 `{ kind, taskKey, detail }`）：
- 派发超时（timeoutExecution）、超支结算（max-tokens）、受阻结算（非 max-tokens 的
  error settle）、陈旧回收（M3）。webhook 关闭时仅日志。

**验收**

- [x] 真实 E2E：强制 800ms 超时 → sink 收到 taskboard.alert（kind=timeout）签名校验通过（E2E-V19-ALERTS-PASS）
- [x] 正常完成不触发 alert（alert 仅在四类失败事件发射）

## 三、实施顺序

G1 → G2 → G3 → G4。（先分类，再对比，再趋势，再触达。）

## 四、破坏性变更与回滚

纯加法：stats 新字段、webhook alert 事件。`git reset --hard v1.8.0` 可回滚。

## 五、验证清单

**代码层**：check/build 全绿；G1/G2/G3 单测。
**集成层**：真实 E2E——G4 sink 收 alert 验签；/stats 含新字段。
**上屏层**：3099 统计区渲染失败分布/agent 对比/CFD（bundle 核对）。

## 六、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 失败分类误判 | 低 | 模式匹配 blockedReason；`other` 兜底；文档列明口径 |
| agent 对比未做难度归一化 | 中 | 文档显著标注「对比需难度归一化，否则误伤难任务多的 agent」 |
| CFD 计算量（N×14×段） | 低 | 几百任务可接受；活动流保留上限限制历史深度 |
| alert 风暴 | 低 | 仅四类失败事件；webhook 可关 |
