# dsh-taskboard 功能缺口与新增建议（全网调研综合分析）

> 方法：3 路并行调研（agent 任务工具生态 / agent 协作模式 / 度量与可观测性），
> 叠加对项目 v1.0–v1.5 的深度掌握，产出「缺失功能全景 + 新增功能建议 + 路线图」。

## 一、定位校准：我们已覆盖主流核心

调研确认我们的 7 态状态机 + 验收标准门 + 结构化证据 + token 预算 + DAG 依赖 +
统计面板，与最接近的竞品几乎同构：

- [OpenClaw Workboard](https://docs.openclaw.ai/plugins/workboard)：9 态状态机、proof/artifacts/claims/attempts/comments 卡片元数据——与我们的 7 态 + 证据结构同构
- [agent-board](https://github.com/quentintou/agent-board)：kanban + requiresReview 质量门 + Board Stats + audit
- [mcp-task-manager](https://github.com/blizzy78/mcp-task-manager)：强制 goal + **definitionsOfDone（验收标准！）** + decompose_task
- [CrewAI Traces](https://docs.crewai.com/edge/en/enterprise/features/traces)：任务级 LLM 调用/token/成本/延迟

**我们更强的**：结构化逐条证据（竞品只有 review 布尔门）、token 预算（输入+输出+实际用量）、
跨进程写守卫、经验卡片、统计面板（lead/cycle/等人/受阻/重做/成功率）。

**最大差距集中在两层**：**协议层（MCP 接入）** 与 **事件层（通知/评论/自愈/恢复/实时推送）**，
以及 **度量→诊断→路由的治理闭环**。

## 二、缺失功能全景（P0/P1/P2）

### 🔴 P0 · 协作闭环（不做就是孤岛）

| # | 缺失 | 主流参照（证据） | 我们的现状 |
|---|---|---|---|
| 1 | **实时推送/通知** | SSE/Webhook/WebSocket 优于轮询；[Google A2A 协议内建 SSE 状态推送](https://github.com/google/A2A)；[Claude Code 社区在要任务完成/等待通知](https://github.com/anthropics/claude-code/issues/28765) | 面板不轮询、无 SSE——另一个会话改看板看不到 |
| 2 | **mid-task 进度可见性** | OpenClaw `heartbeat`/`execution_updated` 事件、worker logs；[LangGraph interrupt + checkpoint](https://docs.langchain.com/oss/python/langgraph/checkpointers) | 子代理只有 settle 一个结果点，执行中无中间汇报 |
| 3 | **有界自动重试（幂等）** | agent-board auto-retry（failed→todo, maxRetries）；[重试需指数退避+熔断+幂等键防重复副作用](https://docs.langchain.com/oss/python/langgraph/checkpointers) | 失败只有人审，无重试；bounce 已可人工重派但无自动路径 |
| 4 | **任务评论/线程** | agent-board comment threads、OpenClaw comments | notes 是单向追加（人→agent），无 agent↔agent 讨论 |
| 5 | **搜索/筛选** | GitHub Projects / Linear / OpenClaw labels+priority（UI 标配） | 面板只有项目下拉 + 状态列，无文本搜索/标签/优先级过滤 |
| 6 | **项目生命周期** | 一切多项目工具 | `task_projects` 只列不建，E1 过滤是死功能（此前已识别） |

**第三路（协作模式）锐化**：HITL 三模式 = approval / editing / review（[OpenAI Agents SDK HITL](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)）——我们有 approval 闸门，缺 **editing（人编辑 agent 中间产物）** 与 **mid-task 转向/暂停**（[Devin Agent Command Center](https://docs.devin.ai/zh/desktop/agent-command-center)、[Temporal signal](https://learn.temporal.io/tutorials/ai/building-mcp-tools-with-temporal/adding-hitl-to-mcp-tools/)）。重试应是「预算决策」：**retry-as-budget**（[重试计入每任务预算](https://mev.com/blog/agentic-ai-orchestration-the-control-layer-routing-retries-approvals-audit-trail)）。等待人工时应可**挂起-恢复**（[agent-sandboxing：等人时容器退出、恢复带全上下文拉起](https://github.com/walkerhughes/agent-sandboxing)）。状态机可扩展一等状态：`retrying` / `paused` / `failed`（[A2A 任务状态机 submitted/working/input-required/completed/failed](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/)）。通知需求有真实用户证据：[Claude Code 要任务完成推送](https://github.com/anthropics/claude-code/issues/28765)、[等待上下文通知](https://github.com/anthropics/claude-code/issues/67165)。

### 🟠 P1 · 生态接入

| # | 缺失 | 主流参照（证据） | 说明 |
|---|---|---|---|

## 二·五、度量治理闭环（P0/P1/P2 —— 度量调研深化）

第三路调研（[Langfuse](https://langfuse.com/docs/metrics/overview)/[AgentOps](https://docs.agentops.ai/v1/concepts/core-concepts)/[DORA in AI era](https://devops.com/why-dora-metrics-look-different-when-ai-is-part-of-your-development-workflow/) 等）的结论：平台擅长「调用层」（trace/token/成本/延迟），**任务板应承担「结果层」聚合**——我们方向正确（activity 流≈trace、/stats≈结果层），但缺「度量→诊断→路由」闭环。升级项按优先级：

### P0 · 把报表变成治理工具
| 能力 | 说明（证据） |
|---|---|
| **成本归因** | `tokensUsed` 只是数字；需 $ 换算、成本/任务、成本/agent/模型、预算阈值告警（[microsoft/agent-governance-toolkit](https://github.com/microsoft/agent-governance-toolkit/blob/main/agent-governance-python/agent-sre/examples/cost_guard.py)、[MLflow 防成本失控](https://mlflow.org/blog/agent-costs-mlflow-gateway/)、[CostHQ](https://github.com/brian-mwirigi/costhq)） |
| **主动告警** | stuck/无限循环/超时/预算超支/成功率骤降——现在是被动查询，应有通知（[agent-watchdog](https://pypi.org/project/agent-watchdog/0.1.3/)、[ivy-heartbeat 自动恢复](https://github.com/jcfischer/ivy-heartbeat/issues/49)） |
| **失败模式分布** | 重做率下钻：loop/stuck/thrash/timeout/上下文溢出/成本失控 分类占比（[agent-vitals](https://pypi.org/project/agent-vitals/1.2.0/)、[infinite-loop 检测](https://futureagi.com/glossary/infinite-loop-agent/)） |
| **CFD 累积流图** | 卡点检测是静态快照，CFD 是趋势版：瓶颈队列可视化 + 交付时间预测（[Adobe](https://business.adobe.com/au/blog/basics/cumulative-flow)、[MPUG](https://mpug.com/visualizing-project-flow-using-cumulative-flow-diagrams)） |
| **agent 维度对比** | 同任务集下 agent/模型成功率/周期/成本切片（[AgentOps tag 切片](https://docs.agentops.ai/v1/concepts/core-concepts)）；**降权前必须先做任务难度归一化**（[FlyRoute](https://www.semanticscholar.org/paper/FlyRoute%3A-Self-Evolving-Agent-Profiling-via-Data-Li-Zhou/329e682b8ab0faf2e52060fe900fb3cdec64799c)） |

### P1 · 指标深化
| 能力 | 说明 |
|---|---|
| **一次成功率** | 首次即成功 vs 重试后成功分开统计（[first-try reliability](https://huggingface.co/papers/2607.02436)）——完成率混入重试样本会失真 |
| **接受率** | 确认完成=接受、打回=拒绝；比内部重做率更接近真实质量（[merge rates falling](https://www.joinnextdev.com/blog/agentic-coding-doubles-prs-but-merge-rates-are-falling)、[GitHub Copilot acceptance](https://docs.github.com/en/copilot/reference/copilot-usage-metrics/interpret-copilot-metrics)） |
| **WIP 限制 + 工作项年龄** | 同时运行 agent 数=WIP，设上限；age 超阈值预警（[Scrum.org 4 flow metrics](https://www.scrum.org/resources/blog/4-key-flow-metrics-and-how-use-them-scrums-events)） |
| **工具调用效率** | 每任务调用数/步数、token/任务（[Thoughtworks 协作质量](https://www.thoughtworks.com/es-es/radar/techniques/measuring-collaboration-quality-with-coding-agents)） |
| **反馈闭环（数据飞轮路由）** | 低成功率 agent 降权/换模型/加验证（[FlyRoute](https://www.semanticscholar.org/paper/FlyRoute%3A-Self-Evolving-Agent-Profiling-via-Data-Li-Zhou/329e682b8ab0faf2e52060fe900fb3cdec64799c)、[loop engineering](https://huggingface.co/datasets/cy0307/awesome-loop-engineering/blob/main/patterns/model-routing-loop.md)） |
| **趋势扩展** | 30/90 天、P50/P95 分位、成功率滑动窗口（均值会被长尾扭曲） |

### P2 · 长尾
用户反馈评分、成本-收益 ROI、预算预测（趋势外推）、模型/版本升级前后回归对比。

## 三、新增功能建议（结合我们独有优势）

调研确认我们独有的：**结构化证据、token 预算、跨进程守卫、经验卡片、统计面板**。建议新增
都建立在这五块上，避免与生态同质化：

1. **证据→可执行验证**：acceptance_criteria 可挂验证命令/脚本，确认完成时可一键执行验证（目前只有 agent 自评 met/note）
2. **失败模式结构化**：settle error 时分类（loop / stuck / thrash / timeout / 成本失控），`stats` 输出失败模式分布——把「诊断」变成度量
3. **接受率**：确认完成=接受、打回=拒绝 → `acceptedRate`（比内部重做率更接近真实质量，回应调研发现的全局 merge-rate 下滑信号）
4. **成本归因 + 预算告警**：`tokensUsed` 已有 → 换算成本 + 超支/逼近预算主动告警
5. **主动告警**：stuck / 超时 / 预算超支 → 通知（先面板内，P1 接 webhook）
6. **mid-task checkpoint 汇报**：子代理执行中周期性注入「进度事件」到活动流（OpenClaw heartbeat 同构），面板显示进行中任务的进度而非只有时长

## 三·五、生态补充观察（第二路调研确认 + 新数据点）

第二路（agent 任务工具生态）完整报告与综合结论一致：**最大差距 = 协议层（MCP）+ 事件层（webhook/评论/重试/链/checkpoint）**。报告额外确认/补充四个我们此前未标注的能力点：

| 能力 | 出处（证据） | 对我们的含义 |
|---|---|---|
| **stale-session 检测** | [OpenClaw Workboard](https://docs.openclaw.ai/plugins/workboard)：卡片带 stale-session 检测，认领会话失联时标记 | 我们有派发超时，但没有「认领会话失联/死亡」的显式标记——被认领任务可能永久停在 in_progress |
| **attempts 元数据** | OpenClaw 卡片元数据 `attempts`；agent-board 自动重试记录每次尝试 | 我们只有活动流里的历史，没有结构化的「第几次尝试」计数 |
| **git worktree 隔离** | [DanWahlin/ai-agent-board](https://github.com/DanWahlin/ai-agent-board)：每任务独立 git worktree 隔离编码 | 面向编码任务的可选增强（任务级工作区隔离） |
| **diff 查看器 / PR 管理** | [ezeoli88/ai-agent-board](https://github.com/ezeoli88/ai-agent-board)：diff 查看、PR 管理 | 证据产物（artifacts）可链接 diff/PR 视图 |

另确认：OpenClaw Workboard 的 `heartbeat`/`execution_updated` 事件与我们的「mid-task 进度」建议同构（第三路协作调研也已独立得出同一结论）。

## 四、建议路线图

| 版本 | 内容 | 对应缺口 |
|---|---|---|
| **V1.6 协作闭环** | 面板实时刷新（SSE/轮询）+ mid-task 进度可见性 + 有界自动重试 + 评论线程（notes 升级）+ 搜索/筛选 + 项目生命周期 | P0 全部 |
| **V1.7 生态接入** | MCP server 暴露 + 签名 webhook + 任务链/流水线 + checkpoint 恢复 | P1 全部 |
| **V1.8 度量治理闭环** | 成本归因（$+告警）、主动告警、失败模式分布、CFD、agent 维度对比（P0 五项）；一次成功率、接受率、WIP/年龄、工具调用效率、数据飞轮路由（P1） | 二·五节 + 新增 1-6 |
