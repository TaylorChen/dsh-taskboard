# dsh-taskboard 功能缺口与新增建议（全网调研综合分析）

> 方法：3 路并行调研（agent 任务工具生态 / agent 协作模式 / 度量与可观测性），
> 叠加对项目 v1.0–v1.5 的深度掌握，产出「缺失功能全景 + 新增功能建议 + 路线图」。

## 一、定位校准：我们已覆盖主流核心

调研确认我们的 7 态状态机 + 验收标准门 + 结构化证据 + token 预算 + DAG 依赖 +
统计面板，与最接近的竞品几乎同构：

- [OpenClaw Workboard](https://docs.openclaw.ai/plugins/workboard)：9 态状态机、proof/artifacts/claims/attempts/comments 卡片元数据——与我们的 7 态 + 证据结构同构
- [agent-board](https://github.com/quentintou/agent-board)：kanban + requiresReview 质量门 + Board Stats + audit
- [mcp-task-manager](https://github.com/blizzy78/mcp-task-manager)：强制 goal + **definitionsOfDone（验收标准！）** + decompose_task
- [CrewAI Traces](https://docs.crewai.com/edge/en/enterprise/features/traces)：任务级 LLM 调用/token/成本/延迟

**我们更强的**：结构化逐条证据（竞品只有 review 布尔门）、token 预算（输入+输出+实际用量）、
跨进程写守卫、经验卡片、统计面板（lead/cycle/等人/受阻/重做/成功率）。

**最大差距集中在两层**：**协议层（MCP 接入）** 与 **事件层（通知/评论/自愈/恢复/实时推送）**，
以及 **度量→诊断→路由的治理闭环**。

## 二、缺失功能全景（P0/P1/P2）

### 🔴 P0 · 协作闭环（不做就是孤岛）

| # | 缺失 | 主流参照（证据） | 我们的现状 |
|---|---|---|---|
| 1 | **实时推送/通知** | SSE/Webhook/WebSocket 优于轮询；[Google A2A 协议内建 SSE 状态推送](https://github.com/google/A2A)；[Claude Code 社区在要任务完成/等待通知](https://github.com/anthropics/claude-code/issues/28765) | 面板不轮询、无 SSE——另一个会话改看板看不到 |
| 2 | **mid-task 进度可见性** | OpenClaw `heartbeat`/`execution_updated` 事件、worker logs；[LangGraph interrupt + checkpoint](https://docs.langchain.com/oss/python/langgraph/checkpointers) | 子代理只有 settle 一个结果点，执行中无中间汇报 |
| 3 | **有界自动重试（幂等）** | agent-board auto-retry（failed→todo, maxRetries）；[重试需指数退避+熔断+幂等键防重复副作用](https://docs.langchain.com/oss/python/langgraph/checkpointers) | 失败只有人审，无重试；bounce 已可人工重派但无自动路径 |
| 4 | **任务评论/线程** | agent-board comment threads、OpenClaw comments | notes 是单向追加（人→agent），无 agent↔agent 讨论 |
| 5 | **搜索/筛选** | GitHub Projects / Linear / OpenClaw labels+priority（UI 标配） | 面板只有项目下拉 + 状态列，无文本搜索/标签/优先级过滤 |
| 6 | **项目生命周期** | 一切多项目工具 | `task_projects` 只列不建，E1 过滤是死功能（此前已识别） |

### 🟠 P1 · 生态接入

| # | 缺失 | 主流参照（证据） | 说明 |
|---|---|---|---|
| 7 | **MCP 协议暴露** | agent-board（12 MCP 工具）、[todo-for-ai-mcp](https://github.com/todo-for-ai/todo-for-ai-mcp)、[GitHub 官方 MCP 支持 Projects](https://github.blog/changelog/2025-10-14-github-mcp-server-now-supports-github-projects-and-more/)、[mcp-task-manager 实测兼容 Copilot/Claude](https://github.com/blizzy78/mcp-task-manager) | dsh 有 `dsh-mcp-client`（生态认可 MCP）但宿主无内置 server；暴露后外部 agent（Claude Code 等）可接入 |
| 8 | **签名 Webhook** | agent-board HMAC-SHA256 + 时间戳防重放 | 任务事件推送到外部系统/其他实例 |
| 9 | **任务链/流水线** | agent-board `nextTask` 完成自动创建下一个 | dependsOn 是阻塞不是自动触发 |
| 10 | **checkpoint/断点恢复** | [LangGraph checkpointers/time travel](https://docs.langchain.com/oss/python/langgraph/checkpointers)、[AutoGPT resume](https://github.com/Significant-Gravitas/AutoGPT/releases/tag/autogpt-v0.5.0)、[Temporal durable execution](https://temporal.io/) | 长任务中断后从 checkpoint 恢复；「等人工时崩溃无法恢复」是真实痛点（[Claude SDK issue #871](https://github.com/anthropics/claude-code/issues/871)） |

### 🟡 P2 · 度量进阶 + 集成

| # | 缺失 | 证据 | 说明 |
|---|---|---|---|
| 11 | **度量升级**：CFD 累积流图、WIP 限制、接受率、per-agent/模型对比、失败模式分布、成本归因（$+告警） | [CFD 能看队列堆积/预测交付（Adobe）](https://business.adobe.com/au/blog/basics/cumulative-flow)；[DORA 警示：AI 让吞吐暴涨但失败率同步上升，完成率↑+重做率↑才是危险组合](https://larridin.com/blog/ai-coding-agent-dora-metrics)；[agentic coding 合并率/接受率在降——「产出被接受的比例」比内部重做率更接近真实质量](https://www.joinnextdev.com/blog/agentic-coding-doubles-prs-but-merge-rates-are-falling)；[失败模式可分类：loop/stuck/thrash/timeout/成本失控](https://pypi.org/project/agent-vitals/1.2.0/) | 我们有结果层聚合（完成/重做/成功率），缺「度量→诊断→路由」闭环 |
| 12 | **度量→路由闭环** | [FlyRoute：成功率/成本 profile → 自适应降权](https://www.semanticscholar.org/paper/FlyRoute%3A-Self-Evolving-Agent-Profiling-via-Data-Li-Zhou/329e682b8ab0faf2e52060fe900fb3cdec64799c)（需先做任务难度归一化，否则难任务多的 agent 被误伤） | 成功率低的 agent/模型自动降权调度 |
| 13 | **外部系统集成** | [GitHub/Linear/Atlassian 官方 MCP](https://aicoolies.com/comparisons/linear-mcp-server-vs-atlassian-mcp-server) | 与 GitHub Projects/Jira 双向同步 |
| 14 | **子任务分解工具** | mcp-task-manager `decompose_task`（含 verification 子任务、同级可并行、critical path） | 复杂任务自动分解 |
| 15 | **任务模板 / 客户视图** | agent-board Project Templates + Client View | 低优先，按需 |

## 三、新增功能建议（结合我们独有优势）

调研确认我们独有的：**结构化证据、token 预算、跨进程守卫、经验卡片、统计面板**。建议新增
都建立在这五块上，避免与生态同质化：

1. **证据→可执行验证**：acceptance_criteria 可挂验证命令/脚本，确认完成时可一键执行验证（目前只有 agent 自评 met/note）
2. **失败模式结构化**：settle error 时分类（loop / stuck / thrash / timeout / 成本失控），`stats` 输出失败模式分布——把「诊断」变成度量
3. **接受率**：确认完成=接受、打回=拒绝 → `acceptedRate`（比内部重做率更接近真实质量，回应调研发现的全局 merge-rate 下滑信号）
4. **成本归因 + 预算告警**：`tokensUsed` 已有 → 换算成本 + 超支/逼近预算主动告警
5. **主动告警**：stuck / 超时 / 预算超支 → 通知（先面板内，P1 接 webhook）
6. **mid-task checkpoint 汇报**：子代理执行中周期性注入「进度事件」到活动流（OpenClaw heartbeat 同构），面板显示进行中任务的进度而非只有时长

## 四、建议路线图

| 版本 | 内容 | 对应缺口 |
|---|---|---|
| **V1.6 协作闭环** | 面板实时刷新（SSE/轮询）+ mid-task 进度可见性 + 有界自动重试 + 评论线程（notes 升级）+ 搜索/筛选 + 项目生命周期 | P0 全部 |
| **V1.7 生态接入** | MCP server 暴露 + 签名 webhook + 任务链/流水线 + checkpoint 恢复 | P1 全部 |
| **V1.8 治理闭环** | CFD/接受率/失败模式分布/per-agent 对比/成本告警 + 度量→路由降权 | P2 + 新增 1-6 |
